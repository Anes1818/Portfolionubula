# Nebula v4: manual activation and merchant checkout

## Delivered software

- Expanded storefront presentation editor: announcement visibility/text, navigation labels, hero eyebrow/headline/description/button text and in-shop destination, photo/layout/badge/note, section titles and introductions, contact hours/details, ribbon/footer text, brand/background colors and optional gentle motion. There are three responsive hero layouts. Instagram handles become safe profile links, and storefront browser titles use the shop's name. A quick customization toolbar and direct click targets show changes immediately in the private canvas; publication still creates the separate live snapshot. Hidden button destinations fall back to a visible section. All merchant content remains escaped plain text, with bounded server validation and backward-compatible defaults. Motion respects reduced-motion settings. This does not change bouquet recipes, pricing, Square settings or activation permissions.

- Free shop configuration and owner preview. One shared app resolves shop slugs from SQLite; it does not create GitHub directories for merchants.
- Owner activation/renewal request saved in the admin directory. Commercial PayPal invoices are arranged outside the app; there is no PayPal API integration or automatic subscription debit.
- Platform admin can record a personally verified USD 29 payment and grant 30 days, extend from the current paid-through date, or suspend access. Fresh admin authentication, optimistic revisions, immutable audit history, operation idempotency and global PayPal-reference uniqueness protect changes. A timed-out request is retried with the same operation ID/reference. A reserved reference is never silently released to a different shop after an unknown outcome; an unresolved conflicting reservation needs operator review.
- Access expiry is checked on public requests in the server. A scheduled job is not required to close new access. Drafts, historical orders and owner access are retained. Activation does not publish an unfinished draft or mark a bouquet paid.
- Explicit merchant approval of exact prices, pickup/delivery, tax rate, delivery fee and fulfillment/refund terms. Missing tax/fees stay unset; enabled checkout requires explicit values. Tax is calculated on items plus delivery, rounded to the nearest cent. A 50% deposit rounds up to the cent. Cash/banknote designs and declared cash products cannot use online checkout pending provider eligibility review; they remain available for enquiries.
- A server-priced immutable order is made from the saved customer request, with design/product snapshot, policy/publication version, final tax/delivery total, customer, terms and expiry. A private 256-bit customer token is stored only as a server hash. The receipt uses a URL fragment/local recovery storage; no bearer token is placed in API paths, queries or provider redirects.
- Merchant-specific Square Hosted Checkout for deposit/full/balance, reusing the existing Ray service's reconciliation and retry logic through a platform adapter. Ray's own source and deployment are unchanged. The adapter supports USD/CAD and the tenant's own selected location/merchant.
- Checkout intent/idempotency key is stored before the provider call. A lost provider response is recovered with that same key. A pending link cannot be silently replaced by a different payment choice. Cancellation reconciles before and after deletion to catch races. Customer design changes create a separate reviewed order; an existing order is immutable and must be cancelled before being replaced.
- Signed Square webhooks route by environment/merchant, fetch authoritative payment/refund records with that merchant's credentials, verify location/currency/amount and never mark return URLs paid. Duplicate events and out-of-order payment/refund signals do not add the same money twice. Refunds or mismatches stop further checkout for review. The first version issues refunds through Square Dashboard.
- Owners see final total, paid, refunded and outstanding amounts separately from fulfillment status. Private receipt recovery works after plan expiry. New charges stop when access/checkout is disabled. Existing provider links may still settle; reconciliation continues so an expiry cannot erase or conceal a payment.
- Square credentials remain encrypted in the tenant's SQLite object. Sandbox and production use distinct keys, cookie names, registry partitions, API hosts and protected settings. Live mode requires explicit server launch approval in addition to production credentials and feature gates.

## Next human setup: real Square Sandbox acceptance

Sandbox OAuth session fix (30 October 2026): authorization now uses `session=true` for Sandbox and `session=false` only for production, as required by [Square's OAuth walkthrough](https://developer.squareup.com/docs/oauth-api/walkthrough). Before connecting in Sandbox, launch the Canadian test seller's Square Dashboard from Developer Console → Sandbox test accounts in the same browser profile, keep that tab open, then begin a fresh authorization from the florist's Square page. Sandbox cannot initiate a seller sign-in on its authorization page. The Square settings page now displays these steps. An old authorization URL is not reusable after restarting the connection, and the single-use browser-bound state/cookie protections remain intact. The fix is covered at both service and HTTP route levels; real provider acceptance is still a separate test.

Sandbox OAuth blank-page resolution (30 October 2026): live Playwright/HTTP diagnostics confirmed that `https://connect.squareupsandbox.com/oauth2/authorize` redirects (302) to `https://squareupsandbox.com/oauth2/authorize`, whose apex domain 301-redirects `/oauth2/authorize/assets/application-*.js` to `https://squareup.com` (HTTP 404), leaving `<div id="root"></div>` unmounted. Routing Sandbox browser OAuth authorization directly to `https://app.squareupsandbox.com/oauth2/authorize` (while keeping server-to-server REST API calls on `https://connect.squareupsandbox.com`) hits the same `oauth-flow-sandbox` service, serves the JS/CSS assets with HTTP 200 on `app.squareupsandbox.com`, mounts the React consent screen (`Authorize` / `Deny`), and shares the exact origin where the Sandbox Seller Dashboard runs when launched from Square Developer Console. In addition, `/dashboard/shop` and `/dashboard/payments` now let florists switch their shop currency (`CAD` / `USD`) to match their Square seller account, `square-storage.mjs` uses `current.draft.currency` immediately, failed OAuth callbacks record and surface `lastError` on `/dashboard/payments`, and `commerce-ui.js` displays an Online Square Checkout Readiness checklist.

Square documents an [Authorize test account shortcut in Developer Console](https://developer.squareup.com/docs/devtools/sandbox/overview#authorize-a-sandbox-test-account): application → Sandbox → OAuth → Authorize test account → select the test seller and required scopes → Save. This can issue a scoped Sandbox OAuth token for independent API testing through API Explorer. It does **not** exercise Nebula's hosted consent/callback flow or automatically connect a Nebula shop. Keep any issued tokens out of chat, Git and browser application code. The existing tenant connection still requires its normal validated OAuth callback; hosted consent acceptance remains outstanding.

## Validation

Publication UX regression: the dashboard and publishing page now expose a copyable, reserved shop URL with explicit private/live status. Blocked publication has an actionable requirements button and nearby reason. Rechecking readiness refreshes access status without discarding the edited draft, and only the checked draft version can publish. A verified platform administrator grants the existing audited seven-day Sandbox entitlement from the **separate operator console**. Florist publishing pages never contain access-grant controls. Browser QA exercises the actual publish button, anonymous storefront access, and the operator grant-to-florist-publication flow. Production merchants still require manually verified activation.

Administration separation: `/admin/login` and `/admin` are the Nebula operator sign-in and customer/subscription console; `/login` and `/dashboard` are the florist sign-in and own-shop workspace. Operator inspection stays under `/admin/shops/:id/preview` or `/admin/shops/:id/orders`, with no florist editing navigation or write controls. An operator can open the separate florist workspace explicitly to manage their own test shop. Entering the operator console never forces shop creation. Ordinary florists see an access-denied page and do not request the operator directory; the server also rejects forged admin headers and all unauthorised admin APIs. Sign-out clears inspected shop/session state, and switching sign-in surfaces resets the return destination. The older apex `/admin.html` continues to hold legacy records; the operator console links to its full absolute URL. Platform-host `/admin.html` bookmarks redirect to `/admin`.

Activation feedback repair: the access panel is near the selected shop's name and shows loading, saving, validation, failure and persistent success messages. All access-changing controls lock while a request is pending. Unknown outcomes keep the exact operation ID and payload across panel remounts; retries cannot silently become a second activation. A 401 exposes explicit Firebase reauthentication (Google or password), then requires the administrator to retry the saved action; verification itself never submits access changes. Password input and in-memory activation fields are cleared after use/sign-out. Loading failures have a retry control. Directory refresh, activation-request/active/suspended filters and selected-row highlighting make updates visible. Completed operations cannot overwrite another selected shop or another signed-in administrator's session. Local browser tests cover delayed real SQLite responses while selecting another florist, 401 recovery, filter results, and a standalone suite covers network failures, frozen retries, validation and detached panels. No live merchant was activated by these automated tests.

102 Node tests pass across the new platform and the existing Ray payment tests; 21 shared recipe/price parity cases also pass. Local verification uses fake identities/provider responses and real local SQLite/workerd. It does not send email, debit a customer, activate a real florist or authorize a real Square account. Node tests cover manual approval/isolation/idempotency, published designs, cents/rounding, USD/CAD deposit/balance/refunds, private receipt access, lost-response retries, invalid signatures, foreign merchant events and price changes. Browser tests exercise manual admin controls, merchant rules and the actual storefront-to-checkout/receipt pages. Existing shared engine identity/parity and request UI regressions remain required.

Free Cloudflare quotas are finite. Per-store financial orders are capped at 1,000 until a retention/archival policy is deliberately implemented; no ledger evidence is silently deleted to make room. Background reconciliation pages ten orders at a time. This is not an unlimited or zero-fee payment service.
